Test strategy · visual regression

What do screenshot tests catch that UI tests miss?

A case study of a drawing-practice timer: compare the changes a screenshot check notices with the changes that functional UI tests notice, then measure how much the image varies without a code change.

Context

Plchldr is a desktop app for practicing from local image folders. Its automated UI tests exercise screens and interactions, while a screenshot layer compares the rendered Electron window with reviewed images.

The question is whether that visual layer catches regressions the UI tests miss—and whether the screenshot comparison can distinguish deliberate visual changes from rendering noise.

Outcome

Run a controlled comparison of injected visual changes, functional UI tests, and screenshot thresholds. Record repeat-render variation and keep the evidence separate from assumptions about performance or reliability.

Key stages

  1. Pin screen size, theme, clock, and random image order.
  2. Apply visual faults and controls to the built renderer.
  3. Run the UI suite and screenshot comparisons against the same screens.
  4. Repeat unchanged renders and compare selected historical changes.

Learning

A passing interaction test is not evidence that the rendered appearance stayed the same. Whether screenshot testing is useful here depends on which visual changes it catches and how much the images move without one.

Next steps

Publish the measurements, their inputs, and their limits together. Electron runs on macOS and CI, CI runtime and flake rate, and mutation score require separate evidence and should not be inferred from screenshot sensitivity alone.
